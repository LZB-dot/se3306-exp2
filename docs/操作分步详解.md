## 2. 任务1 · 井字棋（跟着官网教程手写）

| 步骤 | 做了什么 | 为什么这么做 | 验证 |
| --- | --- | --- | --- |
| 1 | 写 `Square`：只渲染一个按钮，值与点击都从 props 来 | 最小组件，方便后面演示「状态提升」 | 九格能显示 |
| 2 | 写 `Board`：九宫格 + 胜负/平局状态行 | 胜负需要「九个格子的全集」，任何一个 Square 都算不出来 | 三连即出胜者 |
| 3 | `useState` 记录九个格子的值 | 交互数据必须进 state，普通变量改了界面不动 | 落子后界面立刻变 |
| 4 | **状态提升**：把 `history` 与 `currentMove` 提到 `Game` | 时间旅行需要「所有历史快照」，只有顶层能持有 | 回退按钮可用 |
| 5 | 落子用 `squares.slice()` 复制后再改 | React 靠引用变化判断重渲染；且历史快照必须不可变 | 回退后历史没被污染 |
| 6 | `jumpTo(move)` 只改 `currentMove` | 时间旅行的本质就是「改看第几步」，不需要重算棋盘 | 第 n 步棋盘正确 |

**三个自检回答：**

- **Square 有 state 吗？** 没有。它是纯受控组件——值由父组件下发、点击回调给父组件，这也是状态提升能成立的前提。
- **winner 为什么提升到 Board/Game？** 胜负由九个格子共同决定，且 Game 还要对历史快照判定，判定逻辑只能放在持有全集数据的一层。
- **为什么用 `[...squares]` 而不是直接改？** 直接改数组引用不变、界面不更新；而且历史快照会被一并改掉，时间旅行直接失效。

截图：`tic-01-board.png`、`tic-02-win.png`、`tic-03-timetravel.png`。

## 3. 任务2 · 基础训练营 6 练

六练全部写在 `lab2-blog/src/exercises/`，由 `Training.jsx` 用子页签串起来。每练的套路：**目标一句话 → 骨架手写填完整 → 三条验收 → 截图 + 一句话**。

| 训练 | 代码要点 | 验收 | 一句话 |
| --- | --- | --- | --- |
| 1 JSX | `{name}` 插值、`className`、map 渲染列表 | h1 显示变量值、列表无 key 警告、样式生效 | JSX 里变量和表达式写在花括号里 |
| 2 ES6 | 箭头函数 / 解构 / 展开 / map / filter / find / 模板字符串，各写一个可运行例子 | 7 个例子都跑出输出 | 博客最常用的是展开与 map |
| 3 useState | 计数器、受控输入、开关、数组增删改 | 增删改全用 map/filter/展开，无 push | 数组要用新数组替换 |
| 4 key | 可切换 index/id 的列表 + **非受控**输入框 | index 版串位、id 版不串位 | key 是给 React 认节点的 |
| 5 useEffect | 三种依赖形态 + 定时器清理 + 闭包陷阱 | 执行次数说对、卸载无报错、陷阱复现并修复 | 依赖数组决定什么时候重跑 |
| 6 自定义 Hook | 手写 `useWindowSize` | 拖窗口数字实时变、卸载无报错 | 复用的是逻辑不是界面 |

**两个值得记住的坑：**

1. **训练 4 一开始复现不了串位**——受控输入每次渲染都会被 React 强制回写 value，坑被掩盖。改成非受控输入（文字留在 DOM 里）后，index 作 key 删除第一项，「甲-AAA / 乙-BBB」整体前移的现象立刻可见。
2. **训练 5 的闭包陷阱**：`setTimeout` 里直接读 `count` 拿到的是点击那一刻的快照（连点 3 次打印 3 个旧值）；改用函数式更新 `setCount(c => …)` 才是最新值。

## 4. 任务3 · Thinking in React 四步法

文件：`src/thinking/FilterableProductTable.jsx`，照官网「可搜索产品表」示例手写。

| 步骤 | 做了什么 |
| --- | --- |
| 1 拆组件 | FilterableProductTable → SearchBar + ProductTable → ProductCategoryRow + ProductRow |
| 2 写静态版 | 用写死的 PRODUCTS 把界面画出来，**一个 state 都不写** |
| 3 找最小 state | 只有 `filterText` 与 `inStockOnly`；过滤后的列表能算出来，不设 state |
| 4 定位置 | 两个 state 放在共同最近父组件，子组件只拿 props + 回调 |

这一步的方法论直接决定了任务 4 的组件树怎么拆——所以放在博客之前做。

| 步骤 | 对应官网章节 | 这一步具体做了什么 |
| --- | --- | --- |
| 1 | installation | 建项目、理清 `index.html → main.jsx → App.jsx`，清空示例写一个「我的博客」标题 |
| 2 | your-first-component | 按蓝图建 7 个组件骨架（App/Header/PostForm/CategoryFilter/PostList/PostItem/PostDetail） |

| 11 | sharing-state-between-components | `category`、`viewingId` 提升到 App，子组件 props + 回调修改 |
| 12 | reusing-logic-with-custom-hooks | 手写 `useLocalStorage`：惰性读 + JSON 写入，返回值与 useState 同形 |
| 13 | installation | `npm run build` 出 dist，部署到 GitHub Pages |

**第 3 步 Babel REPL 的三条结论**（把 `<div className="box"><h1>你好，{name}</h1></div>` 贴进 babeljs.io/repl 对照）：

1. `className` 不是 `class`：编译后是 JS 对象的 `className` 属性，`class` 是保留字；
2. 插值 `{name}` 变成变量引用，作为 `children` 传入；
3. 标签变成 `React.createElement(标签, props, ...children)` 的函数调用——**这就是「JSX 是语法糖」的证据**；
4. 反向验证 `<Div>`：大写开头被当成组件（引用变量），小写 `<div>` 被当成原生标签字符串。

**API 层为什么这样设计：**

- `api/client.js`：`BASE_URL` 为空即走 mock，接真实后台只改这一个常量。关键是**两条分支都要解出 `data` 再返回**——只 `return mockRequest(...)` 的话调用方拿到整个信封，`posts.map` 直接报 `posts.map is not a function`；
- `api/posts.js`：五个 REST 接口，路径与指导书表格一致；
- `api/mock.js`：4 篇示例文章 + 300ms 延迟；
- 隐形约定：`post = { id: string, title, category, summary, content, publishedAt }`——前端不定义结构，但严格依赖它。
- 定位：按任务书「接口预留」落地，现阶段博客页签由 store 提供数据、远程页签按任务 5 示例直接 fetch；实验三接真实后台时由这一层统一接管，组件代码与接口形状都不用改。

## 6. 任务5 · Zustand + TanStack Query

### 6.1 Zustand：把组件状态升级为全局状态

| 步骤 | 操作 | 为什么 |
| --- | --- | --- |
| 1 | `npm i zustand`，写 `usePostStore.js`：`create(persist(...))` | persist 中间件自动接管 localStorage 读写，省掉手写 `useEffect` 的持久化 |
| 2 | 把 `useState + useLocalStorage` 的 posts 迁进 store，提供 `publish / update / remove` | 改数据的逻辑集中一处，组件里只剩调用 |
| 3 | `partialize: (s) => ({ posts: s.posts })` | 只持久化数据；函数被 JSON.stringify 会丢掉，且没必要存 |
| 4 | 组件里用 **selector 精确订阅**：`usePostStore((s) => s.posts)` | 只订阅用到的字段，避免无关字段变化把组件带崩 |

**验证**：F5 刷新文章仍在（截图 `blog-03-persist.png`；运行日志 `cards after reload: 3`，localStorage 的 `posts` 键里能看到完整 3 条记录）。

### 6.2 TanStack Query：服务端状态

| 步骤 | 操作 | 为什么 |
| --- | --- | --- |
| 1 | `main.jsx` 用 `QueryClientProvider` 包住 App | 不包直接报 `No QueryClient set` |
| 2 | `npx json-server db.json --port 3000 --delay 500` | 真实 REST mock 后台，增删会写回 db.json；`--delay 500` 让 pending 态肉眼可见 |
| 3 | `useQuery({ queryKey: ['posts', port], queryFn })` 渲染三态 | pending / error / success 分别渲染，不写 `loading` 之类的冗余 state |
| 4 | 乐观更新四步：`onMutate`（取消旧查询 + 快照 + 先秒出）→ `onError`（回滚）→ `onSettled`（重拉对齐） | 体验上「秒出」，真相由服务器对齐；失败必须能回滚 |

**queryKey 为什么带 port**：页面上有「把端口改成 3999」的开关用来制造失败，端口变化必须让缓存失效重新取；而它在每次渲染之间是稳定值，不会造成重复请求或缓存串位。

**验证**：`query-1-pending.png`（延迟 500ms 期间）、`query-3-error.png`（停服务/改错端口）、`query-2-success.png`；`query-4-optimistic.png` 发布后新文章秒出、`query-5-settled.png` 重拉后仍在（证明 json-server 真实落库）。

### 6.3 边界三问

| 问题 | 客户端状态 | 服务端状态 |
| --- | --- | --- |
| 数据所有者 | 浏览器（store / localStorage） | 服务器，浏览器只是缓存副本 |
| 换设备还在吗 | 不在，localStorage 不跨浏览器 | 在，重新请求就有 |
| 别人改了要同步吗 | 不用 | 要，所以 `onSettled` 必须 invalidate 重拉 |
